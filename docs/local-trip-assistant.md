# Browser trip assistant

Open `/plan`. Describe a trip, select a route, prepare equipment, and use the packing checklist. The module extends the existing Hyked Fieldbook UI.

## Local model

`@mlc-ai/web-llm` runs Llama-3.2-3B-Instruct-q4f16_1-MLC in a browser Web Worker. Enable local AI explicitly to fetch and cache its model files (~2 GB first download). No Ollama, LM Studio, cloud inference key, or separate installer is needed. A WebGPU-capable Chrome or Edge browser and sufficient memory/storage are required. The local model can rephrase product searches, choose public product links to open, extract specs from fetched page text, and prioritize trip insights. Phone inference is capability-dependent and has not been device-tested.

The model prioritizes available insights using private context. Output is a schema-constrained list of IDs and is validated again before display. It cannot emit new product specs, weather claims, or weights into the plan. This is a constrained planning assistant, not an unrestricted chat model. Trip parsing, route matching, source parsing, math, and packing zones work without AI. The native app can later package model and WASM assets and point WebLLM at bundled URLs; that packaging is not implemented here.

## Data and online sources

- Verified Supabase identity selects only that user's gear, completed hikes, and custom trails. Existing RLS stays in place. No service-role credential is used.
- Account gear is read-only in this module; edits are local overrides. Supplemental gear, preferences, plans, packed checkmarks at save time, and explicit completion feedback are browser-local and account-namespaced. The UI includes an option to forget that local memory. It is not encrypted or synced across devices.
- A profile's explicit comfortable pack weight and daily mileage take precedence over medians learned from completed-trip feedback. Merely saving a plan does not count as trip experience. Recorded hike distance is shown separately from overnight daily mileage.
- Product HTML lookup accepts public HTTPS pages, pins validated public IPv4 DNS results, checks redirects, and limits response size/time. The importer reads Product/ProductGroup JSON-LD, explicit price metadata, and labelled specifications. It fills weight, price with currency, packed size, brand, model/SKU, capacity, materials, dimensions, source URL, and retrieval date when available. Labelled minimum/packaged weights remain distinct. Packed dimensions are separate from floor or deployed dimensions. Users review exact variants before applying facts. Dynamic or blocked pages may require manual entry.
- Without a general search key, product-name lookup supports public manufacturer catalogs from Cascade Designs (MSR, Therm-a-Rest, Platypus, SealLine, PackTowl), NEMO, Big Agnes, and Sea to Summit. Other names use public web discovery with relevance filtering; coverage varies. Public HTTPS manufacturer or retailer URLs can be pasted directly. Trail discovery combines the existing route catalog with Wikipedia discovery links, clearly labelled as leads to verify, not matching itineraries.
- Optional `BRAVE_SEARCH_API_KEY` (server-only) enables general product/trail web search. No key is configured in this checkout, and this provider has not been live-tested. It does not change local model inference. See [Brave's documentation](https://api-dashboard.search.brave.com/app/documentation/web-search).
- Online requests contain search terms or a supplied URL; the model prompt, gear inventory, trip feedback, and profile are not sent to a hosted AI service. Users' own source URLs can of course contain identifiers; avoid private or token-bearing links.
- The Four Pass Loop distance comes from a historical US Forest Service handout. Its permit guidance is obsolete; the interface says so. No current conditions or permits are inferred.

## Product autofill

In Gear or the planner equipment editor, enter the item name or a product link in the normal form, then choose **Fill out parameters**. A link fills unambiguous sourced fields directly; a name opens matching products to choose from. Products with multiple sizes still require an exact variant. The expanded lookup remains available for reviewing individual source fields. This returns focus to the item name. All values remain editable; saving is a separate action. Missing and unselected fields preserve existing manual entries. This source importer works without loading the local model.

The importer never treats shipping weights, an aggregate “from” price, or a currency-less dollar amount as a confirmed specification. Variant-specific NEMO specifications are matched by variant ID; unscoped page facts require explicit confirmation on variant pages. Prices are snapshots, not checkout quotes or exchange-rate conversions. Account totals group currencies separately. Browser-local and saved-plan metadata retain the existing version-1 storage key.

Product regression tests cover extraction, missing fields, variant isolation, price/currency ambiguity, metadata persistence, and separate currency totals. Browser verification exercised both name search (NEMO, exact size selection) and direct URL (MSR), form autofill, focus handoff, desktop/mobile layout, and automated accessibility checks. No existing user gear was modified during these checks.


### Missing account storage

If the server explicitly reports that `gear_items` does not exist, Gear offers the existing browser inventory under the signed-in account’s local storage key. A visible notice explains that these items are local and do not sync. The planner already reads this account-specific local inventory. Authentication, permissions, and network errors do not trigger this fallback. Once cloud storage is provisioned, these local items remain in the planner; migration into the cloud inventory is not automatic.

Product discovery matches whole words and model numbers to exclude unrelated results. Public DuckDuckGo and Bing discovery supplement manufacturer catalogs without a search key. Availability varies by provider.

If a product page blocks lookup or has no readable specifications, the importer searches for the item using the form's name or the URL's descriptive slug. It first checks an indexed excerpt of the same listing, preserving variant IDs and retailer item IDs. Otherwise, it reads up to two matching public alternatives. Recovered results require review before filling the form; they never auto-apply. Search excerpts are labelled unverified and retain a provenance note in saved gear. Alternative-source notes remind users to check the exact model, size and included parts. No measurements are generated from a category average or inferred from a photograph, and no numerical accuracy guarantee is made.

Walmart pages that expose their initial product data can supply item-specific weight, price/currency, model, capacity, materials and packed size. Extraction validates the requested item ID and excludes recommendations and generated summaries. Lookup does not solve retailer challenges or require a browser/model download.

When public sources are unavailable, **Extract details from copied specifications** parses a pasted specification list locally in the browser. Labelled weights, dimensions, materials and explicit price/currency values can fill the existing form after review. Missing fields stay unchanged. Pasted values retain an unverified note; source links and timestamps remain available.

## Nearby trail selection and trip shopping lists

`near` and `around` preserve geographic intent. The planner resolves the town, park or landmark through Photon and asks the user to choose the intended US/Canadian place. It never chooses an ambiguous result silently. A 50 km default radius can be changed to 10, 25, 100 or 200 km. Catalog queries use coordinates rather than requiring the landmark's name in a trail's title. Results never widen outside that radius automatically. Distance is straight-line to the catalog's representative trail point, not a trailhead, driving distance, boundary intersection or nearest point of the full geometry. Broad `in Colorado` searches retain regional matching.

The paginated catalog shows eight selectable sections per page, initially ordered by proximity to the requested mileage (nearest first when no mileage is supplied). Users can switch to geographic proximity. Map/source details open separately, preserving the draft. Selecting a section asks for the intended full-route walking distance, then moves to preparation. Its section provenance and map link remain on the saved trip. No connected multi-day route or camping permission is invented from a short section. Curated guide routes without verified coordinates are excluded from nearby results.

`/api/assistant/places` uses the public Photon HTTPS API for local/moderate use. `PHOTON_API_URL` can point to a compatible hosted service. The proxy validates public addresses, bounds responses and timeouts, coalesces identical requests, caches up to 500 queries for a day and spaces new queries by at least one second per process. See [Photon usage terms](https://photon.komoot.io/) and [deployment guidance](https://github.com/komoot/photon). The public service has no availability guarantee; a scaled deployment needs a suitable provider and shared quotas across instances. Lookup failures expose retry rather than falling back to a different place. The UI credits OpenStreetMap and Photon.

The packing step includes a trip shopping list inferred from trip duration, entered temperature and fuel allowance. Needs are matched against the entire personal inventory using item names (navigation and shelter also use their categories, with shelter accessories excluded). Owned-but-excluded equipment is offered for inclusion rather than repurchase. Suggestions are reviewable, not a certification of suitable ratings, condition, quantities or complete coverage. Users can add custom items, mark obtained/borrowed or not needed, and remove custom items. Add actual obtained equipment through the existing gear editor to include its measured weight. No product price or weight is invented by a shopping status.

Shopping edits, selected place/radius, and trail-section provenance persist in the existing version-1 browser-local saved plans, including backward-compatible validation. Save trip & shopping list is explicit; the normal checklist download includes shopping statuses. Neither list nor geocoding requires the browser model. Guide-route ordering also considers daily mileage preferences, overnight experience and the known selected pack; online research labels publisher, retrieval time and topics without claiming current conditions were verified.

### Deeper product-page extraction

The importer no longer treats a price-only page as a completed weight lookup. It reads the linked page, parses labelled specifications inside Product descriptions and tables, and—when the page identifies a Shopify storefront and weight is still missing—reads that same store's [public product endpoint](https://shopify.dev/docs/api/ajax/reference/product). Locale and product handle are retained. Feed identity is checked before use, variant IDs stay separate, existing source fields are preserved, and fulfillment/shipping weight is never substituted for carry weight. Feed prices require a currency explicitly present in the original product data.

Product reads accept up to 8 MB. Larger HTML pages retain a bounded prefix with unfinished script/style/text fragments discarded, so an oversized recommendations or application-data block no longer discards preceding readable specifications. Other research fetches keep their existing 2 MB limit. DNS/public-address validation, redirect checks and timeouts remain active. Table column and row-group labels are preserved. Measurements can autofill only when their explicit size label matches the selected variant; otherwise the user must select the correct value. Independent repeated weight measurements are rejected rather than reading the first number as universal.

Live verification used the Osprey Australia Atmos AG 65 S/M product link: its former oversized-page failure now fills weight, price/AUD, brand, SKU, 65 L capacity and S/M dimensions into the gear form. The larger variant retains different measurements. This was tested in a temporary non-saving form; no user gear was added or changed. Manufacturer materials without unambiguous variant scope remain reviewable rather than auto-applied.

This expands public-page coverage; it is not a general browser automation service. It does not execute arbitrary retailer JavaScript, log in, solve challenges, or guarantee every retailer is readable. Public alternate sources and local pasted-spec extraction remain available for blocked or unsupported pages.

### Broader product discovery and recovery

Blocked-link recovery now uses the same manufacturer catalogs as name search, alongside public DuckDuckGo/Bing discovery and Brave when `BRAVE_SEARCH_API_KEY` is already configured. One provider failing does not suppress the others. Structured brand/model (or brand/SKU when no model exists) provides a second query. Opaque item links can obtain their name from an exact indexed listing before searching other sellers; Amazon ASIN identity survives equivalent product URL formats. Trademark symbols no longer corrupt model matching.

Recovery reads up to six matching product pages concurrently, including their public storefront feeds, and prefers the matching result with the most available specification fields. Brand confirmation can come from the fetched product's structured data, including consistent brands across variants. Review/comparison pages stay available as research links but cannot automatically contribute comparison-table measurements. Redirected pages must still match the product. Exact-name alternate search excerpts are a last, explicitly unverified fallback when readable pages are unavailable. No missing measurements are fabricated. Existing original-page fields are kept when supplementing a single item, and supplemental source URLs persist in the saved source note. Variants remain separate and require selection.

Default recovery uses a 48-second network deadline, eight-second page budgets and ten-second discovery budgets, with abort signals propagated through HTTP requests and redirects. It uses the existing gear form, requires no model/browser download, and adds no database migration or new required service key.

Verification: all 94 tests pass, scoped ESLint passes, and the production webpack build succeeds. Live Walmart lookup returned the Ozark Trail one-person tent's published specifications. A controlled unavailable-retailer test using live discovery recovered the NEMO Tensor All-Season manufacturer page and all four separately scoped size variants, including weight, packed size and price. That test simulated only the original retailer failure; discovery and manufacturer reads were real network requests. Universal coverage remains impossible where specifications are unpublished, inaccessible or cannot be tied reliably to the requested model.

### Local AI for gear specifications

Gear lookup now connects to the browser-local Llama 3.2 / WebLLM worker. Enable **Use local AI to research missing details** for automatic fallback after public lookup, or use **Enable local AI & read page** on a readable result. When search returns several links, the model can pick the best product pages for the app to open and read. The first use downloads and caches model files; inference runs in the browser, with no separate app or cloud inference service. WebGPU and sufficient memory are required. Loading progress, cancellation, errors and retry remain in the existing gear editor. A selected size is required before reading variant specifications.

The server returns at most two bounded, visible-text passages from product pages it actually read. Scripts/navigation are excluded. The local model proposes missing fields and exact source quotes, and deterministic validation rejects values absent from their quote, altered quotes, partial numeric substrings, unsupported units/currencies, shipping/fill weights and replacements for existing sourced fields. Extracted values require review before applying, carry a local-AI source note, and preserve source links. Empty or unsupported model answers leave existing gear unchanged. A model cannot provide page content when access is blocked; this distinction is stated in the UI.

Public catalog lookup precedes network lookup. The initial catalog contains one explicitly sourced record: Walmart item **5128730697**, Ozark Trail **W2201**. Its specifications and observed USD price were checked on September 24, 2026 UTC. The price is labelled as a dated observation, not a live quote. This record resolves only that exact item with its default seller and no alternative variant/offer parameters. Other item IDs are not inferred from this record. Advertising parameters are removed before page requests while item, seller and variant selections remain intact.

Verification reproduced the missing-data response on the deployed app for the user's Walmart link while a local network read returned the item details. In Chrome, a real browser-model inference on a declared synthetic narrative extracted a supported weight and material; the actual gear editor then accepted the user's full advertising URL and filled the tent's weight and packed dimensions through the public catalog. Test gear was not saved. The temporary test page was removed. The browser test tab closed during the mobile-width check, so that visual check was not completed; its viewport override was reset.

Product research now proceeds from a name directly to reading up to three matching public product pages. Broad searches retain a choice list, and redirected pages must still identify the requested model. Exact catalog aliases (including “Ozark Trail solo tent”) work without an online search. Local AI is enabled by default for missing information, with the first-use model download disclosed and an opt-out checkbox. If a name search has no results, the on-device model may propose up to two constrained rephrasings; the app executes those searches and reads matching pages. Rephrasings cannot introduce model numbers, sizes or arbitrary new brand names. Source-backed catalog, alternate-page and local-AI results can fill the existing form directly when using Fill out parameters; saving the gear is still explicit. Ambiguous size and search-excerpt values retain review. Model errors preserve already-found fields.
